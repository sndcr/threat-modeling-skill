# Ground truth: jobline-async

Change: Moves job execution out of the submit request into a new RabbitMQ-driven worker that claims leased runs from job-orders, reads input with auth-issued job tickets or through an egress proxy, and reports back, adding PASETO service tokens, NetworkPolicies, an outbox, a sweeper and exactly-once metering.

## Must find
- data-service-legacy-path-bypasses-tickets: Ticket scoping (spec §8.3, plan Task 16) applies only to requests that present a service token; until the last rollout step (spec §13 step 5, plan Task 22 step 5, INTERNAL_CALLER_AUTH in plan Task 16) the data service still trusts any internal caller by network position (spec §1), while spec §8.4 lets the worker reach data :8080 and the worker processes tenant jobs from rollout step 2 onward. A compromised worker, the component that parses tenant files (spec §12), simply omits the token and ticket and reads any tenant's datasets, so the spec §12 blast-radius claim is false for the whole migration. It may stay false: spec §13 step 5 requires rejecting token-less internal callers, but no plan task gives the existing data-service callers (inventoried only for NetworkPolicy in plan Task 19) or job-orders' sync path an identity allowed to request svc:data (spec §8.1 table), so enforcement either breaks them or never ships. Fix: onboard every existing caller to service tokens and switch the data service to enforce before any tenant is enabled for async execution. (min: Medium)
- cleartext-residual-risk-misscoped: Spec §12 accepts cleartext internal traffic because an observer supposedly gets at most a 5-minute single-audience token or one run's ticket, but the same network carries minting-grade and static credentials: the projected ServiceAccount tokens sent to auth (spec §8.1, valid 10 minutes and replayable to mint every audience the SA may request), job-orders' svc:auth token, which is enough to have auth sign tickets for any tenant_id and dataset_ids because auth checks only ID formats and the TTL cap (spec §7, plan Task 3), and long-lived RabbitMQ passwords on unencrypted AMQP (spec §5, plan Task 10). One captured job-orders to auth exchange plus any worker svc:data token (holder is the shared svc:worker, spec §8.2) reads any tenant's datasets while the tokens last, and a captured worker AMQP password lets an attacker keep draining jobs.execute so runs never execute. How much worse this is than today depends on whether the §12 attacker can also send traffic that the NetworkPolicies admit, which the documents don't settle. Fix: restate the residual risk, put server-side TLS (not mTLS, so within the non-goals) on auth :8081 and AMQP, and reconcile issued tickets against claimed runs with alerting. It counts when at least one credential that can mint tokens or tickets (the projected SA token sent to auth, or job-orders' svc:auth token) is reported open as exposed on the plaintext network; the other credentials and the §12 framing strengthen it but aren't required. `[ACCEPTED]` citing spec §12 doesn't count for this item: §12 accepts replay of 5-minute single-audience tokens and one run's ticket, not the minting-grade and static credentials this item is about. (min: Medium)
- no-per-tenant-admission-or-fairness: Async execution removes the backpressure the synchronous request imposed (spec §1, §2): submit returns 202 after validation, every tenant shares one FIFO queue consumed with prefetch 1 (spec §5, §6), each order can hold a worker for up to max_duration_s (3600 s default) on each of 3 attempts, and a tenant URL that stalls or returns 5xx makes each attempt retryable (spec §11), yet neither the spec (§4, §5) nor the plan (Task 7, Task 12) limits queued or running runs, submit rate or worker share per tenant. One tenant can enqueue thousands of long orders and delay every other tenant's jobs for hours; the plan even load-tests 100k queued runs (plan Task 23). The documents mention no gateway rate limit, and even with one each accepted request amplifies into up to about 3 worker-hours. Fix: per-tenant caps on queued and running runs enforced at submit (429) and at claim, and fair scheduling across tenants (per-tenant queues or a claim-time quota check in job-orders). (min: Medium)
- worker-hardening-spec-plan-gap: Spec §12 says the worker, which renders tenant-supplied files, runs non-root with a read-only root filesystem, but no plan task builds that: the worker deployment in plan Task 18 sets only the scratch volume, grace period and mounts, with no securityContext (readOnlyRootFilesystem, allowPrivilegeEscalation, dropped capabilities, seccomp), and plan Task 12 gives only a non-root Dockerfile UID. This is a spec-plan gap; it counts when reported as one or as a missed control row. A renderer exploit then gets a writable root filesystem and default capabilities in the pod that holds the worker's credentials. Fix: add the securityContext the spec requires to plan Task 18, with a test that the deployed pod has it. (min: Low)
- render-shares-worker-credentials: The render subprocess (plan Task 13, Task 15) exists to protect the event loop and has only CPU and memory rlimits, so it runs as the worker's UID with the worker's credential files (the projected SA token plus the RabbitMQ and object-storage Secrets, plan Task 18, which also contradicts the spec §12 statement that the projected token is the only mounted credential) and its network paths to job-orders :8081, data :8080, auth :8081 and the egress proxy, which gives internet egress on 443 for exfiltration despite the no-direct-egress framing in spec §8.4. A parser bug triggered by a tenant file becomes the worker's full identity: mint svc:job-orders and svc:data tokens, consume and claim every tenant's runs and complete them with forged reports, and read any tenant's data through the legacy data-service path. Severity depends on how exploitable the renderer is, which the documents don't say. Fix: render in a separate sandbox (own container or UID with no credential mounts and no network, seccomp or gVisor) that receives only the input file. (min: Medium)
- job-ticket-not-bound-to-lease: A ticket lives for claim time plus max_duration_s plus 5 min (spec §8.2, plan Task 6), and the data service checks only signature, tid, dataset_ids and that holder equals the service token's sub (spec §8.3, plan Task 16), where holder is the shared identity svc:worker rather than a pod or lease. A worker that lost its lease, whose run was requeued to another worker or has already finished keeps read access for up to about an hour, every retry mints another valid ticket, and a leaked ticket works with any worker pod's token, so the spec §8.3 statement that the worker "can only act for runs job-orders has leased to it" and the holder-binding mitigation in spec §12 are overstated; the plan's gap list (G9c) records this and changes nothing. Exposure is limited to data the run was entitled to, which keeps the floor low. Fix: issue short tickets bound to lease_id and renewed through the heartbeat response, stop renewing on lease loss or terminal state, and bind holder to the pod identity TokenReview reports. (min: Low)
- verification-key-configmap-unprotected: Spec §8.2 makes the jobline-token-keys ConfigMap the trust anchor for every token and ticket, and verifiers accept any k4.public entry for a purpose and hot-reload changes within about 30 s (plan Task 1), but no task restricts who can update the ConfigMap, makes it immutable or alerts on changes (plan Task 2 only checks that auth's active key is present, not that no other key is). Anyone with ConfigMap write access in the jobline namespace, often granted to deploy pipelines and developers more widely than Secret access, can add a key and forge svc:job-orders and svc:worker tokens and tickets for any tenant without touching auth's signing Secret. Severity depends on cluster RBAC, which the documents don't describe. Fix: restrict updates with RBAC resourceNames and an admission policy, use immutable versioned ConfigMaps, and alert on any change. (min: Medium)
- proxy-dns-oracle-internal-names: The submit check is syntactic and accepts internal names such as single-label hosts or names ending in .svc.cluster.local (spec §4, plan Task 7), the proxy resolves through kube-dns (plan Task 17), which answers cluster names and any private zones it forwards to, and a name that resolves into a denied range yields the distinct permanent code input_url_blocked while an unresolvable or failing host yields input_fetch_failed, both shown to the tenant with the attempt count (spec §4, §9.6, §11, plan Task 14). A tenant can therefore map which internal service and corporate hostnames exist, despite the spec §9.6 promise that the tenant does not learn what the proxy saw. How clean the oracle is depends on how Smokescreen signals DNS failures, which plan Task 14 leaves to confirm. Fix: resolve tenant hosts through a public-only resolver, reject cluster and private suffixes at submit, and return one indistinguishable code for blocked and unresolvable hosts. (min: Low)
- sync-path-bypasses-egress-controls: The §9 SSRF controls apply only to the worker, yet every tenant starts on the synchronous path (the flag defaults off, plan Task 22), where job-orders still fetches tenant URLs directly from its pod (spec §1), and the plan keeps a job-orders to internet NetworkPolicy exception and the direct fetch until the sync path is removed (plan Task 19, Task 22). Because the submit check is syntactic and does not restrict the port (spec §4, plan Task 7) and the DNS-time checks exist only in the proxy (spec §9.2), a sync-path tenant can submit an https URL whose name resolves to a node, the API server or another internal HTTPS service and get the response or its status back through the report or failure message for the whole migration; if the exception is written as a broad ipBlock it also re-admits in-cluster ranges. It is pre-existing behaviour, which keeps the floor low. Fix: route sync-path fetches through the egress proxy from rollout step 2, the plan's own stated alternative, and allow job-orders egress only to the proxy. (min: Low)

## Must not claim
- token-forgery-or-confusion: The claim that PASETO tokens can be forged through JWT-style algorithm confusion or an unsigned token, that a user token can pass as a service token or ticket (or the reverse), that a service holding only the public keys can sign tokens, or that an on-path attacker can swap the verification keys. PASETO v4.public fixes Ed25519 with no negotiable algorithm and only auth holds the private keys (spec §8.2, plan Task 2); each purpose has its own key, kid set and implicit assertion, and verifiers look kids up only in that purpose's set and require a single matching aud (spec §8.2, plan Task 1, with cross-purpose rejection tests); public keys arrive by mounted ConfigMap, not over HTTP (spec §8.2). Forging through access to key material is a different, valid threat and is not this claim: reading or replacing the signing Secret, adding a key to the ConfigMap (verification-key-configmap-unprotected), or minting through a captured bootstrap or service token (cleartext-residual-risk-misscoped).
- duplicate-delivery-double-completion-or-billing: The claim that at-least-once delivery, sweeper races or a partitioned worker can produce two committed results or two usage records for one run. Every transition is a single conditional UPDATE, complete and fail require the current lease_id, and a late complete gets 409 lease_lost (spec §3, §11, plan Task 5, Task 6); usage is written only by job-orders in the terminal transaction with a unique run_id and ON CONFLICT DO NOTHING (spec §10, plan Task 4, Task 5), with concurrency and partition tests (plan Task 5, Task 23). Duplicate execution can happen, but it cannot commit or bill twice.
- forged-queue-message-controls-execution: The claim that anyone able to publish to or tamper with the cleartext AMQP stream can make a worker fetch an attacker-chosen URL, pick a tenant or read someone else's data. The message carries only schema, run_id, order_id and enqueued_at with no tenant, input, URL or credentials, and a worker must claim the run from job-orders, which decides from its own database (spec §5, §6, §7; plan Task 8 asserts the payload shape); a forged message can at most trigger a rejected claim or run a run that is already legitimately queued and due (spec §5, tested in plan Task 23), and the worker's RabbitMQ user cannot publish (spec §5, plan Task 10).
- worker-url-fetch-reaches-internal: The claim that a tenant URL can make the worker reach in-cluster, node or metadata addresses (through DNS rebinding, redirects, IP-literal encodings or a non-443 port), or that the DNS-dependent checks run only at submit. The proxy resolves once, dials the resolved IP and denies loopback, private, link-local including 169.254.169.254, CGNAT, ULA and cluster ranges on port 443 only (spec §9.2, plan Task 17), backed by the proxy's own NetworkPolicy (spec §9.3, plan Task 19); every redirect hop is re-validated through the proxy (spec §9.4, plan Task 14), IP literals in every encoding are rejected at submit (spec §4, plan Task 7), and the worker has no direct egress (spec §8.4). Distinct from sync-path-bypasses-egress-controls (job-orders' direct fetch during rollout) and proxy-dns-oracle-internal-names (an existence oracle, not a fetch).
- cross-tenant-read-via-order-or-message: The claim that a tenant can read another tenant's dataset by naming its ID in an order (dataset IDs are not checked at submit), or that a tenant or the queue message can set the tenant used for tickets and result keys. The tenant comes from job-orders' own run row in the claim response (spec §6, §7), only svc:job-orders may request tickets (spec §7, plan Task 3, tested in plan Task 23), the data service takes scope only from the ticket's tid and filters tenant_id and dataset_ids inside the query, returning 404 for IDs not under tid (spec §8.3, plan Task 16), and job-orders re-checks result keys against a prefix built from the database row and serves downloads only from the stored key (spec §12, plan Task 6, Task 7). Distinct from data-service-legacy-path-bypasses-tickets, where a compromised worker skips the ticket path entirely, and from cleartext-residual-risk-misscoped, where a captured job-orders token mints tickets.
- cleartext-is-new-or-unanalysed: The claim that the change introduces unencrypted internal traffic, or that the design doesn't analyse the cleartext exposure. Internal HTTP is already plain with no service authentication (spec §1), and spec §12 analyses the exposure and accepts it with compensating controls. Recommending TLS, mTLS or a mesh as a countermeasure is not this claim; the valid finding is that §12 mis-scopes what crosses the wire (cleartext-residual-risk-misscoped).
- internal-api-exposed-via-gateway: The claim that tenants or the internet can call the internal run, token or ticket endpoints through the gateway. They listen on a separate port :8081 the gateway doesn't route, and a CI check fails any route to :8081 or /internal (spec §7, plan Task 20); plan Task 3 tests that /internal returns 404 on :8080, and every internal route also requires a service token for its audience (spec §7, plan Task 6).
- delivered-result-overwrite: The explicit claim that overwriting a result object changes what a tenant downloads. Bucket versioning is on, complete records the uploaded object's version_id after a HeadObject check, and downloads fetch that exact version from the key stored on the tenant's own order (plan G6, Task 6, Task 7, Task 18); the worker has no delete permission (plan Task 18). A general statement that leaked worker credentials allow tampering under results/ is not this claim (object tagging, for one, is still possible), and a compromised worker can still complete runs it claims with forged content (render-shares-worker-credentials).
