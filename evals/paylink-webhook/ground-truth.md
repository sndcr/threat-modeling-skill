# Ground truth: paylink-webhook

Change: adds a public, HMAC-signed Paylink webhook (POST /v1/webhooks/payments, app/webhooks.py + app/schemas.py, wired in app/main.py:8,11) that marks invoices paid and moves subscriptions to active/past_due.

## Must find
- empty-secret-fallback: webhooks.py:22 falls back to `""` when PAYLINK_WEBHOOK_SECRET is unset (and `os.environ.get` returns `""` as well when it is set but empty), so the check at webhooks.py:23-24 still passes for anyone who signs with the empty key. An anonymous internet caller can then forge `invoice.paid` for any invoice id (ids are sequential integers) to mark it paid and activate its subscription, or forge `invoice.payment_failed` to push any tenant's subscription to `past_due`. It should fail closed (refuse to start or reject every request). (min: High)
- no-replay-or-idempotency: webhooks.py:27-38 never checks `event.id` or `created` (schemas.py:12-14), so an old signed body (captured, logged, or simply redelivered by Paylink) is applied again, e.g. an old `invoice.payment_failed` replayed after payment sets the subscription back to `past_due`. There is no store of processed event ids and no timestamp window. (min: Medium)
- event-not-bound-to-invoice: webhooks.py:28 looks the invoice up by `data.invoice_id` alone and never checks the event's `subscription_id`, `amount_cents` or `currency` (schemas.py:6-8) against the stored invoice. Any payment that reaches Paylink with that invoice_id, whatever its amount or currency, marks the invoice paid (webhooks.py:33), and any failed payment naming it sets that invoice's subscription `past_due` (webhooks.py:36). If a payer or tenant can set invoice_id or amount on its own payment at the processor, it can settle a large invoice with a small payment, or fail a payment on purpose that names another tenant's invoice and push that tenant to `past_due`. (min: Medium)
- no-state-transition-guard: webhooks.py:32-36 sets states with no check of the current state: `invoice.paid` turns a `void` invoice into `paid` and a `canceled` subscription into `active` (webhooks.py:34), a paid event for one invoice sets the subscription `active` while another of its invoices is still unpaid or failed, and a late `invoice.payment_failed` sets `past_due` even when the invoice is already `paid`. Paylink may deliver events out of order, so this goes wrong even without an attacker. (min: Medium)
- unbounded-body-before-auth: webhooks.py:21 reads the whole request body into memory and HMACs it before any authentication or size limit, on an anonymous public endpoint, so large bodies cost memory and CPU per request. (min: Low)
- non-constant-time-signature-compare: webhooks.py:24 compares the signature with `!=` rather than `hmac.compare_digest`. It is not practically exploitable over the network (see must-not-claim), so the Hardening note is the right place for it, unrated; a findings row at Low also counts. The fix is one line.
- no-audit-trail-of-state-changes: webhooks.py:32-38 changes billing state in the system of record without recording the event id, event type or previous status, so a disputed status change (paid, past_due) cannot be traced to the Paylink event that caused it, and duplicates cannot be detected afterwards. It also counts when another open row's countermeasure explicitly records the event id, type and previous status of each change. (min: Low)

## Out-of-change leads
- billing-endpoint-cross-tenant: main.py:46-49 `/v1/billing` selects the lowest-id Subscription and the newest Invoice with no tenant filter, so every tenant sees a subscription and an invoice that are usually another tenant's. It has the same shape as the webhook's lookup at webhooks.py:28 (a query with no tenant scope), which is how the variant scan reaches it; the webhook also now drives the status fields this endpoint leaks.

## Must not claim
- missing-signature-header-bypass: leaving out X-Paylink-Signature does not skip the check: the header defaults to None (webhooks.py:18), and `None != expected` returns 401 (webhooks.py:24).
- signature-parser-mismatch: the HMAC is computed over the raw body bytes (webhooks.py:21-23), and those same bytes are what gets parsed (webhooks.py:27). A claim that the signature covers a re-serialized or different view of the payload is wrong.
- webhook-lacks-api-key-auth: calling the missing X-API-Key on the webhook an auth bypass is wrong. The route is meant to be called by Paylink, not tenants (docs/specs/paylink-webhook.md:21-24), and the HMAC is its authentication.
- sql-injection-via-invoice-id: `invoice_id` is a pydantic `int` (schemas.py:5) passed to `db.get` (webhooks.py:28), a parameterized primary-key lookup. There is no injection path.
- practical-remote-timing-forgery: rating the `!=` comparison (webhooks.py:24) High/Critical as a practical way to forge signatures over the internet overstates it. Recovering a full HMAC-SHA256 hex digest through network timing on a Python string compare, behind a TLS gateway, is beyond practical.
- payload-subscription-id-used: the event's `data.subscription_id` (schemas.py:6) never picks the subscription that changes: the handler updates `invoice.subscription`, the one the stored invoice points to (webhooks.py:34,36). A claim that a forged or mismatched subscription_id lets the sender activate or suspend a subscription of its choosing is wrong.
- anonymous-invoice-enumeration: an anonymous caller cannot enumerate invoice ids through the 404 at webhooks.py:29-30, because the signature check at webhooks.py:24 returns 401 first. The only way past it is the empty-secret fallback, which is its own finding.
- plaintext-api-keys-as-change-finding: models.py:13 stores API keys in plaintext and auth.py:15 looks them up by raw equality. This is pre-existing (docs/specs/paylink-webhook.md:39 calls it the accepted mechanism) and shares no code shape with the change, so scoring it as a finding row of this change is wrong. Mentioning it as an out-of-change lead, or not at all, is fine.
